CLI 0.4.4はgatewayのtools probeで協調決済の結果が曖昧になったとき、確定済みのchannelイベントを照合する。証拠が揃わなければ、結果不明のまま再送を止める。

通信の失敗だけでは、channelが決済されたかどうかは決められない。新しいprobeは、その曖昧さを二度目のcloseへ変えず、確定済みの履歴へ追いかける。

FLOPPER FEEDは公開npmのSDK 0.5.2とCLI 0.4.4を取得し、registryのSHA-1・SHA-512と照合した。前回のCLI 0.4.2記事より後の新規公開だ。今回の差分は、決済結果の照合、バックアップ再開状態の置き場所、session用palletの正式名への対応にある。

OUTCOME RECONCILIATION

probeが確かめるもの

配布CLIは、協調決済の送信を試す前に確定済みの開始ブロック高を記録する。送信の呼び出しが例外になっても、probeの期限内で同じchannelのイベントを前方へ探す。対象イベントと同じextrinsicの成功も必要になる。

  • A

    Settled成功には仕事量の合計が一致し、協調決済フラグが立ち、minerへの支払額が正であることが必要。

  • B

    同じchannelのTimedOutRefundedは返金結果になる。仕事量の不一致と支払額ゼロは別の診断結果で返す。

  • C

    開始時の確定headが取れない場合や、走査期限まで結果が出ない場合は、再送しないよう明記した結果不明を維持する。

適用範囲はgatewayのtools qualification probe。この変更だけで、すべてのdirect sessionや公開Issueの決済問題が解決したとは言えない。

同時に出た新しい差分

CLI 0.4.4 / BACKUP

再開記録をcheckpointのそばへ

CLI 0.4.4はdownload receiptを既定で--model-dirの隣へ置く。--state-dirを指定する場合も同じファイルシステムが必要で、配布コードはdeviceの一致を検査する。metadata-only onboardingが提案するbackupコマンドにも、登録済みprecisionが渡るようになった。

ストリーミング経路自体は0.4.2で導入済み。今回は再開記録の配置とprecisionの受け渡しが新しい。

SDK 0.5.2 / SESSION HTLC

session用palletの正式名へ対応

SDK 0.5.2はsession付きHTLC作成で、従来の別名より先にflopSessionKeysとFlopSessionKeysを探す。変更履歴は支出上限の事前検査、署名者ごとのnonce、wrapperのエラー処理を維持するとしている。配布resolverを確認したが、署名付きHTLCは送っていない。

CLI 0.4.3がSDK依存の下限を0.5.2へ上げ、0.4.4も維持している。既報の登録待機30秒・120秒は変更されていない。キャッシュされたallowanceの期限切れ経路は、引き続き運営側の更新を求める。
