FLOP’s network repository now has a shared workflow for service release notes. It checks the source, commits the notes and prepares a draft. A person still makes the release public.

No published entries yet.

The public releases API returned an empty list during our 12 November check. The new workflow and subscription instructions are on main; production staging has not been demonstrated in this report.

One place to follow the notes

Two 11 November merges extend flop-labs/network beyond bug intake and triage. PR #105 added a reusable staging workflow and reader instructions. PR #211 added five image-service names to its existing source allowlist. This is a new publication route, separate from the npm packages covered in our previous report.

Each release is meant to carry notes only. GitHub’s generated source archives contain the network repository, not the service’s implementation. A release entry here should not be read as a downloadable service binary.

From source to public entry

  1. SOURCE CHECK

    Accept an authorized service

    The script checks a service/source pair against the allowlist, validates the version and requires nonblank notes. Its textual filter also refuses selected private-repository, internal-host and IPv4-like content.

  2. NOTES COMMIT

    Give this version its own commit

    It writes the notes under releases/<service>/<version>.md. The new commit becomes the target for that service’s release tag.

  3. DRAFT

    Create or update the draft

    A rerun can update an existing draft. An already published release is refused before a notes write. The workflow serializes the same service/version while allowing different release groups to run separately.

  4. HUMAN PUBLICATION

    Let a person publish

    The API payload asks for draft: true and make_latest: false. The script stages the announcement; it does not perform the final publication step.

The content filter is a bounded text heuristic. Its presence does not establish that every possible secret or internal reference will be detected.

Twelve checks with a fake GitHub CLI

12 / 12local cases passed

We retrieved the public script and test at commit b8a9a88, matched their Git blob IDs and ran the unchanged test program locally. Its fake gh records intended API calls instead of contacting GitHub. All 12 cases passed.

The cases cover first draft creation, draft updates, one retried commit, three exhausted commit attempts, refusal of a published release, source/service permission checks, version and note validation, and the three text-filter examples.

No GitHub App was created, no workflow was dispatched and no remote note, tag or release was written by this check. PR #105 describes a GitHub App and caller secrets as setup prerequisites. Their present configuration is unverified.
