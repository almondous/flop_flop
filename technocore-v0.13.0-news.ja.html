前回記事の追跡訂正

v0.12.1記事ではpasskey identity pathの設計を紹介した。新releaseによると、sign inが反応せず、その後の操作もreloadまで塞ぐことがあった。修理版がv0.13.0だ。以前のversionを信頼できるpasskey baselineとして扱わないでほしい。

v0.13.0の主題は明確な境界だ。browser ceremonyにはdeadline、MCP listingにはmaximum、POST uploadには10秒。拒否されるsigned conditionは、検証前にrequestのreplay counterを消費しなくなった。

3つの故障、3つの具体的修理

完了できない処理を待ち続けない

PASSKEY / PENDING
次の試行が詰まった処理を置き換える

pageはceremonyをabort可能なcontrollerで保持し、自前のdeadlineを強制する。WebAuthnが使えない環境では、失敗しかできないbuttonの代わりにidentity seed pathを案内する。

REPAIRED
MCP / 3.2 MB
list_notesのdefaultは50件へ

wrapperは要求されたlimitを1から200へclampし、省略したkey数も報告する。直接の/kv/<namespace> routeは変更されず、引き続き全件を返す。

BOUNDED
SIGNED GET / 400
replay counterを使う前にconditionを検証

不正なconditional note writeは失敗した後、他は有効なsigned requestまで再試行不能にしていた。GETも、すでに安全な順序だったPOST laneへ合わせた。

loadへ時計と天井を付けるrelease

10秒、50 keys、約6 warnings

10 strickleを含むPOST upload全体のdeadline。時間切れは408を返しconnectionを閉じる。
50MCP list_notesのdefault。callerは最大200まで指定できる。
≈ 6残りbudgetが少ないbandで、全replyではなく約6回に絞られるwarning。

caller固有のbudget footerを間引くことで、通常readをCDNで共有できる機会が増える。note readもcache可能になるが、caller自身のbudget値を載せるreplyは引き続きno-store。rate limitが消えたり429がなくなったりする変更ではない。

MCPのsigned send toolは、single line処理で空になる内容をexternal signing challengeより前に拒否する。変更せず再試行しても成功不能なchallengeへ署名を求めなくなった。

出典: PR #731、uploadとcleanupの境界 · PR #730、共有可能read · PR #761、空内容の拒否

Trust boundary

説明が改善しても、contentはtrustedにならない。

conditional writeの409は、返すvalueが別caller由来でuntrustedだと明示するようになった。value自体はcompare and setへbyte単位で再利用できる。instructionではなくdataとして扱う。
