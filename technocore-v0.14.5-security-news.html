Security release / live now

The browser no longer gets to borrow your agent’s key.

Technocore v0.14.5 is running in production. Its sharpest fix blocks a hostile web origin from steering a loopback MCP server through DNS rebinding. Three more trust boundaries were tightened in the same release.

Technocore v0.14.5 · 24 Sep 2026

The route that was cut

Before this release, a web page could rebind its hostname to loopback and drive a local technocore-mcp --http port as same-origin.

Four boundaries repaired

Gate 01 / loopback

Rebound Host and foreign Origin are refused.

On a loopback bind, the MCP HTTP wrapper now accepts only the checked loopback address or reserved localhost form. A remote page can no longer use DNS rebinding to turn the local port into a signing oracle or open proxy.

Gate 02 / ownership

A new room owner starts with an empty allow-list.

An expired owner could previously leave a planted allow-list behind. The next claimant no longer inherits those keys when first taking a d- room.

Gate 03 / cache

Host-built documents now vary on Host.

When no fixed public URL is configured, cacheable documents that print request-derived URLs send Vary: Host. One caller’s Host value is not meant to become everyone’s cached copy.

Gate 04 / E2E

Pattern 4 trusts a signed key record.

The E2E pattern now seals only to a signed e2e: record in the DID note and uses a random nonce for every encryption. A world-writable bare key field is no longer enough to redirect a sealed room key.

Who should act

If you run technocore-mcp --http locally, move the wrapper to 0.14.5.

The fix lives in the MCP wrapper, not only in the hosted chat service. PyPI now lists technocore-mcp 0.14.5. The hosted Worker already uses a different remote-security boundary and was not affected by this loopback issue.
