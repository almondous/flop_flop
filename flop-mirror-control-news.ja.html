CLI 0.5.0が、モデルの配布先をpublisher自身で更新するコマンドを追加。DAバックアップを結び付けた後は、metadataだけの実行からも、2チャンクの抜き取り検査を経て承認へ進める。

CLI 0.5.0 / SDK 0.6.0

CLI 0.5.0

既存の権限に、新しい操作口。

FLOPは11月12日、CLI 0.5.0とSDK 0.6.0をnpmで公開した。新設のflop model mirrors setでは、モデルのpublisherがcontent rootを変えずに配布先のヒント一覧を更新できる。コマンドは確定済みチェーン状態を使い、署名者が登録publisherであることを確認する。

前回のストリーミングbackupはデータを準備する段階だった。今回はmirror更新の専用コマンドに加え、DAの結合が済んだmetadata-only実行から承認へ進む経路が加わった。準備から承認への引き継ぎが具体化している。

配布先、結合、検査。

配布先を選ぶ

model mirrors set

HTTPS、Hugging Face、ModelScope、DAの参照に対応。DA参照は有効なLeased blobである必要があり、providerは確定状態から取得する。空でない最終一覧は最大8件。--clearは一覧を空にする。

--appendは確定済みの既存項目を保持して不足分を追加する。すべて登録済みなら変更せず終了。ただし一覧を読んでから置き換えるため、同じpublisherの並行更新を上書きする可能性がある。

承認の前に結び付ける

model onboard --approve

metadata-onlyでの承認には、モデルの登録とDA weightsの結合が必要。公開手順はbackup、commitment指定のupload、DA file-table mirrorの追加、その後の承認再実行となる。必要な結合がなければ、この承認経路はチェーン書き込み前に停止する。

mirrorのURLは取得先のヒントにとどまる。registrarやRootが、このコマンドでpublisherの更新権限を代行することはできない。

確定状態と計画を比べる

--dry-run

mirrorコマンドは、検証後に署名前のencoded callを表示できる。出力には確定済みの一覧、要求する一覧、追加分が含まれる。

送信結果が不明なら、再送の前に確定済み一覧を読むのが文書化された手順。今回の取材ではモデルを変更する操作は実行していない。

2

2チャンクは、抜き取り。

新たなmetadata-only承認の前に、結合済みDA imageからランダムな2チャンクを検査する。chunk commitment、対象ファイル全体のSHA-256、固定したHugging Face revisionの該当bytes、paddingを確認。承認根拠を再読し、imageやtableが変わっていれば拒否する。

リリースはこれをspot checkと明記している。モデル全体の証明ではない。paid admissionは引き続きindependent-audit-unavailableで停止する。

容量予約も、確定状態から

CLI 0.5.0はminer capacity-rate showも追加。SDK 0.6.0の容量予約読み取りを使う。SDKの対象specは1014015〜1014020で、今回の公開RPC読み取りは1014020だった。これは互換対象の範囲であり、minerの認定や推論成功を確認した意味ではない。

結果不明を、結果不明のまま扱う

SDK 0.6.0では、曖昧な結果の後にfaucet POSTを自動再試行しない。拒否と結果不明を分ける詳細APIも追加。残高が十分というだけでは、その請求に対応する入金の証拠にしない。認証されたrequestとtransactionの結び付きがない現行方式では、詳細なfunding helperは成功応答も結果不明として扱う。

確認範囲：両npm配布物のSHA-1・SHA-512 integrityを照合し、mirror・承認の配布コードと公式CLIノートを読んだ。GPU認定、DAダウンロード、モデル承認、署名、有料推論は未実施。朝の確認で公開GitHub Releases APIは空だった。ノートのcommitとnpm公開は別々の事実として扱う。
